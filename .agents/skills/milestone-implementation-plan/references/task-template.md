# 面向 Codex 的阶段实施任务书模板

> 这份文件是**输出结构模板**，不是要机械地逐字填充的表单。按任务裁剪章节；一个有实际内容的短章节优于大量空洞小节。常规完整版约 12–20 节。写给执行 Agent 的内容使用祈使语气，不使用“我们接下来可以……”的规划口吻。

```md
# Task: Mx.y — [English Technical Title]

## 1. 项目背景与已确认的技术决策
- 项目目标、技术栈、Monorepo/运行环境（经核实的信息）。
- 已实施与尚待核实的前置模块；本阶段与上下游的关系。
- 需要延续的关键技术决策，不重做已有效的系统。

## 2. 开始前：仓库审查
- 查看 Git 工作区、AGENTS.md、PRD、技术文档、相关实际代码与测试。
- 记录与文档不一致的地方，优先适配实际公开 API。
- 旧代码或归档目录只读；不覆盖用户改动。

## 3. 核心目标与完成后的可见效果
- 用一句话描述主目标。
- 列出 3–7 个必须完成的结果。
- 给出一个端到端的最小可运行链路（如 UI → Controller → Worker → Core → UI）。

## 4. 架构、包职责和依赖边界
- 新能力放在哪里，各层为何存在。
- 哪些依赖允许，哪些禁止；不得重复实现已有算法。
- 数据所有权和层级边界（必要时）。

## 5. 接口与数据契约
- 输入、输出、错误、事件、类型约束、版本约束。
- 选用精简 TS 伪代码解释契约，并注明以现有接口为准。
- 明确类型/单位/索引空间/空值规则（相关时）。

## 6. 核心实现步骤
- 步骤 A：核对现有模块并确定适配位置。
- 步骤 B：实现最薄必要的基础组件。
- 步骤 C：对接既有能力，不重写算法。
- 步骤 D：完成跨包/跨线程/跨 UI 集成。
- 步骤 E：处理真实失败路径和资源清理。
- 不要泛泛写“实现核心功能”。每项明确触发、操作与产出。

## 7. 领域不变量与兼容性
- 算法、确定性、物理量、ID、缓存、性能等本任务适用约束。
- 明确何种变化属于正常版本演进，何种变化属于回归。

## 8. 运行时与生命周期 [按需]
- 任务状态、错误传播、并发策略、取消、释放资源、重试边界。
- 如果与任务无关，直接删除本章。

## 9. 缓存、数据传输及内存 [按需]
- 缓存 Key、失效传播、TypedArray/Transferable 所有权。
- 内存成本与可测量的限制。
- 无缓存时不要为了模板强行设计。

## 10. Web / CLI / Demo 集成 [按需]
- 说明现有展示或运行入口如何接入；最小可见验收。
- 不提前建设正式产品模块来服务短期调试。

## 11. 建议目录结构
- 只列应新增/调整的关键文件，先核实实际路径。
- 不机械生成空目录/空模块。

## 12. 测试矩阵
- 正常功能、极值/边界、无效输入、失败/取消、重复调用、跨模块兼容。
- 固定 Seed/golden fixture 等领域回归（适用时）。
- 必要的浏览器真实环境验证，Mock 不可替代真实集成。

## 13. 性能与资源指标 [按需]
- 明确采样规模、对比口径、实际记录项目。
- 不虚构性能数据，不用依赖机器速度的严格阈值。

## 14. 明确不属于本阶段的内容
- 列出 5–10 个容易越界的具体功能；不是泛泛“不要过度设计”。
- 如要调整已有算法/数据模型，只允许基于明确原因最小修改。

## 15. 验收标准（Definition of Done）
- 6–12 个可以被开发者亲自验证的条件。
- 既包含核心代码，也包含与实际入口贯通的完整流程。
- 列出重要负向条件（不修改旧代码、无无关重构等）。

## 16. 验证命令
- 使用仓库实际支持的 package manager 和 script。
- 可举例 pnpm typecheck/lint/test/build，但先检查命令是否存在。
- 如无法跑浏览器测试，须明确报告。

## 17. 最终交付报告
- 修改文件、设计与接口、重要取舍、运行方式。
- 实际执行的检查及结果、性能数据、已知问题、规划差异。
- 建议下一阶段，但不要自行开始。

## 18. 执行边界
- 不修改旧归档代码，不覆盖用户改动，不自动 Git commit/push。
- 本任务开始前先审查真实代码，然后直接实施，而不是停在设计。
- 仅对真正无法解决的阻塞问题提出澄清。
```

## 输出精度要求

- 使用项目真实名称、阶段号、目录；没核实到的路径明确标“示意/按实际调整”。
- 不把完整参考模板贴给最终用户后又另发一个同义的摘要。产出一份可独立复制的完整任务书即可。
- 拒绝以“增加适当测试”“优化性能”“支持取消”等不可验证语句充当验收条件；写出判定条件。
- 不要让当前 Skill 直接执行代码变更：上述“直接实施”是下一位执行 Agent 的任务指令。
- 如果用户只希望当前阶段的“执行方案”，不强制给逐行代码或安装命令；重点保证接口与职责边界清晰。
