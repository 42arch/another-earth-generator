# 球面世界生成与二维地图投影方案

## 1. 文档目的

本文描述奇幻地图生成器从当前“有边界的二维平面地图”演进到“球面世界统一数据源”的总体方案，并给出一条可分阶段实施、可以持续验证、不会一次性推翻现有功能的技术路线。

目标不是先渲染一个 3D 地球，再把渲染结果截图或烘焙成二维图片，而是：

> 在球面网格上生成唯一的一份地理数据，再将这份数据分别交给二维投影渲染器和三维地球渲染器。

```text
确定性种子
   │
   ▼
球面网格与地理生成管线
   │
   ├── 球面坐标 + 高程颜色 ──► 3D Globe
   │
   ├── 等距圆柱投影 ──────────► 2D 世界地图 / 纹理导出
   │
   └── 墨卡托等其他投影 ──────► 2D 交互地图
```

这样能够保证二维与三维模式中的大陆、岛屿、板块、高程、海岸线、河流和气候数据一致，并从拓扑层面解决经度方向的接缝问题。

---

## 2. 当前方案的局限

当前项目以 `DiagramMesh` 为核心，在矩形区域内使用平面 Delaunay/Voronoi 网格。生成器和渲染器普遍依赖以下平面概念：

- `regionX`、`regionY`；
- `width`、`height`；
- 到矩形边界的距离；
- 平面欧氏距离；
- 存在凸包边界的半边结构；
- 基于二维坐标采样的噪声。

为了改善当前二维地图的视觉边界，项目还使用了 overscan 和视口安全区。这对于独立的海报式地图是合理的，但不适合作为全球地图的数据模型：

- 左右边缘在拓扑上不是邻居；
- 二维噪声在左右两侧通常不连续；
- 大陆生成会受到矩形边界影响；
- 板块与海洋盆地会感知并响应不存在于真实星球上的边界；
- 将最终二维 heightmap 直接包裹到球体时，会在经度接缝处产生断裂；
- 平面区域数量不能准确代表球面面积，尤其是在采用经纬网格时。

因此，未来的全球模式不应继续以二维 heightmap 为权威数据源。

## 3. 总体设计原则

### 3.1 球面数据是唯一真源

全球模式下，高程应被定义为球面表面上的标量场：

```text
elevation: S² → R
```

每个球面区域保存一个高程值。二维投影和三维地球只负责把该区域放到不同的显示位置，不重新生成高程。

同样的原则适用于：

- 板块编号和边界类型；
- 陆地、海洋与湖泊分类；
- 大陆和岛屿归属；
- 降水、温度、通量；
- 河流路径和海岸线；
- 用户手工编辑结果。

### 3.2 生成逻辑与显示投影解耦

生成器不应知道画布尺寸、墨卡托投影或 3D 相机。生成器只允许依赖：

- 球面区域的三维单位向量；
- 纬度、经度；
- 区域邻接关系；
- 球面距离与区域面积；
- 确定性随机数。

投影器只负责将球面坐标转换为二维坐标。渲染器只负责消费投影后的几何。

### 3.3 一个球面拓扑，多种显示视图

当前平面地图代码可以保留作生成效果和交互方式的参考，但新架构不再长期维护两套权威世界数据：

- `sphere`：唯一的世界生成拓扑，没有生成边界；
- `globe3d`：直接消费球面位置和球面 Voronoi；
- `map2d`：将同一份球面 Voronoi、海岸线和属性数组投影到平面。

二维投影不是独立的 `DiagramMesh` 世界，修改投影、中央经线或画布尺寸不得改变地理数据。

### 3.4 投影切口不是世界边界

球面没有左右边界，但任何矩形世界地图都必须选择一条经线切开。切口只能影响二维显示，不能影响大陆、板块或高程的生成。

即使采用球面数据，二维地图中的大陆仍可能被切口分到左右两边。这不是数据断裂，需要由投影层通过以下策略处理：

- 允许选择中央经线；
- 自动寻找穿过海洋最多的切口经线；
- 将跨切口的海岸线、河流和多边形拆成两段；
- 必要时在左右两侧复制跨界几何；
- 横向平移地图时使用周期性 wrap。

## 4. 推荐的球面网格

### 4.1 方案比较

| 网格方案 | 优点 | 主要问题 | 建议用途 |
| --- | --- | --- | --- |
| 经纬度规则网格 | 实现简单，天然适合 2:1 纹理 | 极区严重收缩，邻接和面积不均匀 | 最终纹理输出，不作为模拟核心 |
| 细分二十面体 Icosphere | 没有边界，面积较均匀，邻接稳定 | 12 个五邻接顶点，需要自行构造球面单元 | 推荐作为核心世界网格 |
| Cubed Sphere | 适合纹理分页和 GPU 采样 | 六个面之间仍需处理跨面索引 | 高分辨率 GPU 模拟备选 |
| Fibonacci 点 + 球面 Delaunay | 点分布均匀，外观自然 | 构网和稳定排序较复杂 | 非规则球面 Voronoi 备选 |

首选 Icosphere。它与当前“区域 + 邻接关系 + TypedArray 属性”的架构最容易衔接。

### 4.2 Icosphere 数据组织

从二十面体开始，每次细分将一个三角形拆成四个三角形，并把新增顶点归一化到单位球面。细分层级与规模大致为：

| 细分级别 | 顶点数 | 三角形数 | 建议用途 |
| ---: | ---: | ---: | --- |
| 4 | 2,562 | 5,120 | 快速预览、单元测试 |
| 5 | 10,242 | 20,480 | 均衡交互与低性能设备 |
| 6 | 40,962 | 81,920 | 默认高质量交互与导出 |

可将 Icosphere 顶点作为 region，将三角形作为球面单元之间的拓扑连接。大多数 region 有 6 个邻居，原始二十面体对应的 12 个 region 有 5 个邻居。

为了兼容海岸线、多边形和点击拾取，还需要构造其对偶球面 Voronoi：

1. 计算每个球面三角形的球面中心；
2. 收集与某个 region 相邻的所有三角形；
3. 在该 region 的局部切平面中按角度排序；
4. 排序后的三角形中心组成该 region 的球面多边形。

### 4.3 建议的底层数组

球面网格仍应坚持 TypedArray，以控制内存和 GC：

```ts
interface SphericalMeshData {
  numRegions: number
  numTriangles: number

  // xyz 均为单位球面坐标，数组长度为 numRegions * 3
  regionPosition: Float32Array
  regionLatitude: Float32Array
  regionLongitude: Float32Array
  regionArea: Float32Array

  // CSR 邻接结构
  neighborOffsets: Uint32Array
  neighbors: Uint32Array

  // 三角面索引
  triangles: Uint32Array
}
```

`regionArea` 非常重要。全球陆地覆盖率、降水总量和统计信息应按球面面积加权，不能简单使用 region 数量。

区域面积总和应接近：

```text
4πR²
```

如果内部使用单位球面，则面积总和应接近 `4π`。

## 5. 网格抽象与坐标系统

### 5.1 生成器依赖球面 region 图，不依赖 DiagramMesh

建议先引入最小的公共拓扑接口。不要在第一阶段强迫所有代码使用完整、复杂的抽象，只抽出生成器实际需要的能力：

```ts
export interface WorldMesh {
  readonly kind: 'sphere'
  readonly numRegions: number
  readonly regionArea: Float32Array

  forEachNeighborOfRegion: (region: number) => IterableIterator<number>
  distanceBetweenRegions: (a: number, b: number) => number
}
```

坐标能力可通过判别联合或专门的几何接口提供：

```ts
export interface SphericalGeometry {
  readonly regionPosition: Float32Array
  readonly regionLatitude: Float32Array
  readonly regionLongitude: Float32Array
}

export interface PlanarGeometry {
  readonly regionX: Float32Array
  readonly regionY: Float32Array
  readonly width: number
  readonly height: number
}
```

这样可以避免在球面实现中伪造没有意义的 `width` 和 `height`。旧平面生成器后续不再接入新 `WorldMesh`，需要复用的算法应提取为只依赖 region 邻接的独立函数。

### 5.2 球面距离

两个单位向量 `a`、`b` 的球面夹角为：

```text
θ = acos(clamp(dot(a, b), -1, 1))
distance = R × θ
```

当只做候选排序时，可直接比较点积或弦长，避免大量调用 `acos`：

```text
chord² = 2 - 2 × dot(a, b)
```

局部方向、板块速度和风向不能存成全局二维向量，而应存储在区域的切平面中。每个位置可建立 east/north 基向量，或者直接存三维切向量并确保：

```text
dot(position, tangentVelocity) = 0
```

## 6. 无缝高程与噪声

### 6.1 使用三维噪声采样球面

全球模式不能再直接使用 `noise2D(longitude, latitude)`。经度虽然可以周期化，但极区仍会发生收缩和方向奇异。

推荐对单位球面位置使用三维 Simplex Noise：

```ts
const index = region * 3
const x = position[index]
const y = position[index + 1]
const z = position[index + 2]

const value = noise3D(
  x * frequency,
  y * frequency,
  z * frequency,
)
```

分形噪声可以继续叠加多个 octave。由于球面同一点只有一组 xyz 坐标，经度接缝两侧必然得到相同值。

### 6.2 高程不是纯噪声

噪声只应用于中小尺度细节。整体高程仍应由地理过程共同决定：

```text
基础大陆轮廓
  + 板块汇聚形成的山脉
  + 板块分离形成的洋中脊
  - 海沟与深海盆地
  + 多尺度球面噪声
  + 后续侵蚀或平滑
```

海平面继续作为统一阈值。第一版 3D 渲染保持固定半径，高程只用于颜色和地理分类：

```text
renderPosition = unitPosition × planetRadius
```

第一版禁止将高程写入顶点半径。未来如果增加可选的视觉夸张，它也只能是渲染参数，不能写回权威高程。

## 7. 生成管线迁移

### 7.1 板块生成

当前板块生成可以迁移为球面多源扩张：

1. 在球面上均匀选择板块种子；
2. 使用图距离、球面距离或带权多源 BFS/Dijkstra 分配 region；
3. 为每个板块生成三维切向速度；
4. 在相邻板块边界比较相对速度；
5. 根据法向分量和切向分量分类汇聚、分离与转换边界。

球面板块不存在靠近地图边缘的特殊情况。所有边都应有相邻三角面，所有 region 都应处于闭合拓扑中。

### 7.2 大陆生成

全球模式中的大陆生成应删除以下逻辑：

- 到矩形边缘的距离；
- `edgeOceanMargin` 安全区；
- overscan；
- 可视窗口内的种子限制。

应保留并迁移：

- 基于邻接关系的多源生长；
- 大陆面积分配；
- 紧凑度、延伸度和海岸粗糙度；
- 板块吸引与板块边界影响；
- 确定性随机顺序。

大陆覆盖率需从“region 数量比例”改为“球面面积比例”。生长终止条件应检查累计 `regionArea`，而不是仅检查累计 region 数量。

大陆形状的方向性可定义在种子点的局部切平面。对于跨度非常大的大陆，固定切平面会失真，需要使用球面测地距离或沿生长前沿动态平行运输方向。第一版可以使用测地半径与板块吸引，暂时弱化超大尺度的椭圆轴约束。

### 7.3 岛屿生成

岛屿仍可保留沿海型、群岛型、火山链型和散布型。需要调整：

- 岛屿间距使用图距离或球面距离；
- 火山链方向位于局部切平面；
- 跨越经度切口的岛链仍是同一个连续群组；
- 不存在二维视口安全掩码；
- 目标面积使用球面面积。

### 7.4 海洋、湖泊与 Feature 分类

当前平面算法通常可以从网格边界开始泛洪，将与边界连通的水体定义为海洋。球面没有边界，因此必须更改判定方式。

推荐流程：

1. 找出所有低于海平面的水域连通分量；
2. 计算每个分量的球面面积；
3. 默认将面积最大的水域分量定义为全球海洋；
4. 其余封闭水域定义为湖泊；
5. 如果未来允许多个互不连通的大洋，可增加面积阈值或显式 ocean seed。

这是球面迁移中最容易遗漏、也最需要单独测试的一项。

### 7.5 海岸线

不建议先投影成二维栅格再提取海岸线。应直接在球面拓扑中寻找陆地 region 与水域 region 的共享边，形成球面海岸线环。

二维显示时再投影这些环，并在投影切口处分段。3D 模式则直接使用球面顶点绘制。

球面上不存在开放到世界边界的海岸线路径；正常海岸线应形成闭环。

### 7.6 河流与水文

第一版纯地形球面河流已经实现：

- 使用 Priority-Flood 解决封闭洼地；
- 海洋和湖泊 region 都是天然排水出口；
- 每个陆地 region 使用自身球面面积作为均匀径流；
- 汇流面积、下游指针、源头和河段全部保存为球面权威数据；
- 河口落在陆地与水域 Voronoi 单元的共享边界；
- 跨投影切口的河流路径必须在渲染阶段拆分，数据层保持连续。

本阶段不引入降水、蒸发、季节或风场。未来气候模型只需替换每个 region 的初始径流权重，不改变排水拓扑和河网数据接口。

### 7.7 气候

球面模式为气候模型提供了更合理的输入：

- 纬度直接决定基础太阳辐射；
- 可加入轴倾角和季节；
- 风向是球面切向场；
- 水汽输运沿球面邻接关系进行；
- 海陆热力差异与洋流可以逐步加入。

第一版可以先使用纬度、海拔和到海洋的图距离生成温度与降水，再逐步实现环流。

## 8. 二维投影层

### 8.1 投影接口

建议将投影定义成独立策略：

```ts
interface MapProjection {
  readonly id: string
  readonly wrapX: boolean

  project: (
    longitude: number,
    latitude: number,
    centralMeridian: number,
  ) => { x: number, y: number } | null

  unproject: (
    x: number,
    y: number,
    centralMeridian: number,
  ) => { longitude: number, latitude: number } | null
}
```

投影输出可以先使用归一化坐标，再乘目标画布尺寸。`unproject` 用于二维模式下的点击、笔刷和区域拾取。

### 8.2 等距圆柱投影

建议把等距圆柱投影作为第一种实现，因为它：

- 可以表示整个球面；
- 天然输出 2:1 世界纹理；
- 公式简单，容易验证；
- 适合导出给 3D 引擎作为球体纹理；
- 极区虽然失真，但不会无限发散。

归一化公式为：

```text
x = wrap(λ - λ₀) / 2π + 0.5
y = 0.5 - φ / π
```

其中 `λ` 是经度，`φ` 是纬度，`λ₀` 是中央经线。

### 8.3 墨卡托投影

墨卡托投影适合交互浏览和局部方向保持，但不能显示真正的南北极：

```text
x = wrap(λ - λ₀) / 2π + 0.5
y = 0.5 - ln(tan(π/4 + φ/2)) / 2π
```

实现中必须将纬度限制在约 `±85.05112878°`。因此：

- 3D Globe 仍显示完整两极；
- 墨卡托视图会裁掉极冠；
- 如果二维模式必须显示整个世界，应切换到等距圆柱或折衷投影；
- 不应因为墨卡托不可见而删除极区数据。

### 8.4 切口处理

任何投影路径在绘制前都必须执行 seam splitting。简单判定方式是：如果相邻投影点的横向距离超过画布宽度的一半，就说明路径跨越了切口。

需要分别处理：

- 海岸线闭环；
- 河流折线；
- 湖泊多边形；
- 板块边界；
- region 填充三角形。

不能直接连接切口两端，否则会在整张地图上画出一条横线。对于填充多边形，可将跨界顶点的经度进行 unwrap，然后分别裁剪到左右视口，并在另一侧生成副本。

### 8.5 自动选择中央经线

为了减少重要大陆被切开，可以在生成完成后统计不同经度带上的陆地面积，选择陆地面积最小的经线作为切口。

这个选择只存入视图配置：

```ts
interface ProjectionViewState {
  projection: 'equirectangular' | 'mercator'
  centralMeridian: number
}
```

修改中央经线不得触发地图重新生成。

## 9. 3D Globe 渲染

3D Globe 已使用 Three.js 作为独立 WebGL 渲染器，球面 Voronoi 单元作为地表显示几何。后续 PixiJS 二维视图只消费球面数据的投影结果。

3D 渲染需要的核心数据已经存在于球面网格中：

- Icosphere 三角形索引；
- region 或 vertex 的单位球面位置；
- 高程；
- 地表颜色、海洋颜色和气候属性；
- 河流与海岸线路径。

第一版采用以下方式：

1. 从 Icosphere 三角形构造球面 Voronoi 对偶；
2. 每个 Voronoi cell 使用统一的高程、地形或板块颜色；
3. 所有地表顶点保持固定半径，不创建高程位移；
4. 海岸线沿 Voronoi 共享边界绘制；
5. 等高线在 Icosphere 标量场上使用 marching triangles；
6. 相机支持旋转、缩放和精确 region 拾取。

高分辨率版本可改用纹理、法线贴图和 LOD，但这些不应成为球面数据 MVP 的前置条件。

## 10. 二维与三维编辑同步

编辑必须作用于同一份 `MapData`：

- 二维模式：先通过 `unproject` 将指针位置转换为经纬度，再寻找最近球面 region；
- 三维模式：通过 raycast 找到球面三角形或 region；
- 两种模式最终都修改相同的 `rawElevation[region]`；
- 修改后只重新计算受影响的派生数据和两套渲染几何。

笔刷半径应使用角距离或实际球面距离，而不是屏幕像素。UI 可以继续显示像素大小，但内部需要先根据当前缩放转换为球面半径。

## 11. 推荐的代码结构

下面是目标结构示意，不要求一次性全部创建：

```text
src/core/
├── mesh/
│   ├── world-mesh.ts
│   ├── planar/
│   │   └── diagram-mesh.ts
│   └── spherical/
│       ├── icosphere-builder.ts
│       ├── spherical-mesh.ts
│       └── spherical-voronoi.ts
├── geometry/
│   ├── spherical-math.ts
│   └── tangent-frame.ts
├── projections/
│   ├── projection.ts
│   ├── equirectangular.ts
│   ├── mercator.ts
│   └── seam-splitter.ts
├── generators/
│   └── 现有生成器逐步改为依赖 WorldMesh
├── renderers/
│   ├── planar/
│   └── globe/
└── world-engine.ts
```

`MapData` 中的标量属性数组可以继续沿用。`TectonicData` 中的板块质心和速度需要由二维分量迁移或扩展为三维分量，例如：

```ts
interface SphericalTectonicData {
  regionPlate: Int32Array
  plateSeeds: Int32Array
  plateArea: Float32Array
  plateCentroid: Float32Array
  plateAngularVelocity: Float32Array
  regionBoundaryType: Uint8Array
  regionStress: Float32Array
}
```

其中 `plateCentroid` 和 `plateAngularVelocity` 都按 xyz 三分量连续存储；局部切向速度由角速度与区域位置的叉积按需计算。

## 13. 测试与验收策略

### 13.1 球面拓扑测试

- 每条边必须恰好属于两个三角形；
- 邻接关系必须对称；
- 不存在边界 region；
- 满足球面欧拉示性数 `V - E + F = 2`；
- Icosphere 只有 12 个五邻接顶点，其余顶点通常为六邻接；
- regionArea 总和接近 `4π`。

### 13.2 投影测试

- `unproject(project(point))` 在容差内回到原点；
- 经度增加 `2π` 后投影 x 等价；
- 等距圆柱可以表达南北极；
- 墨卡托超过有效纬度时正确 clamp 或返回不可见；
- 跨切口路径不会出现超过半个画布宽度的错误线段。

### 13.3 生成测试

- 相同 seed、网格级别和参数生成完全相同的 TypedArray；
- 不同中央经线不会改变生成数据；
- 陆地覆盖率按面积统计达到配置目标；
- 海洋和湖泊分类不依赖投影切口；
- 三维噪声在任意经线切口处连续。

### 13.4 二三维一致性测试

- 同一 region 在 2D 和 3D 中具有相同高程与 feature；
- 2D 投影点反算后能够命中同一球面 region；
- 切换渲染模式不会修改 `MapData`；
- 编辑、撤销和重做作用于共享数据，而不是渲染副本。

## 14. 性能与内存注意事项

- 生成阶段优先操作 region 索引和 TypedArray，避免创建大量 `{x, y, z}` 临时对象；
- 邻接关系建议使用 CSR 数组，避免为每个 region 创建 `Set` 或独立数组；
- 球面距离排序优先比较点积或弦长，最后需要真实距离时才调用 `acos`；
- 三维噪声可以逐 region 计算并缓存多尺度结果；
- 投影几何可以按“投影类型 + 中央经线 + 网格版本”缓存；
- 修改投影只重建二维几何，不重新运行地理生成管线；
- 修改高程时尽量只更新顶点缓冲和受影响的水文/等高线数据；
- 高级别 Icosphere 的生成可迁移到 Web Worker，避免阻塞 UI。

## 15. 主要风险与应对

### 15.1 抽象范围过大

风险：试图一次性让所有生成器同时兼容平面和球面，导致长期不可运行。

应对：先完成球面网格、噪声和投影技术验证，再按板块、大陆、高程、水文、气候的顺序迁移；每个阶段都保持一个可展示结果。

### 15.2 球面几何数值问题

风险：点积越界、极点局部坐标退化、球面多边形排序错误。

应对：所有 `acos` 输入 clamp 到 `[-1, 1]`；切平面基向量使用稳定的参考轴；为五邻接顶点、极点和跨切口路径设置专门测试。

### 15.3 投影切口产生错误几何

风险：海岸线横跨整张地图、填充三角形覆盖错误区域。

应对：将 seam splitting 做成独立模块；所有二维矢量渲染都必须经过该模块，不允许每个 renderer 自己实现一套切口判断。

### 15.4 二维投影效果与旧平面效果存在差异

风险：球面世界投影后的大陆和单元不会与旧 `DiagramMesh` 平面世界逐像素一致。

应对：旧平面模式只作为视觉参考，逐项迁移颜色、等高线、河流和交互表现；地理数据一致性以球面世界为准。

### 15.5 3D 范围膨胀

风险：过早投入材质、大气、云层和复杂光照，延迟核心数据闭环。

应对：3D 第一版只做固定半径、Voronoi 单元色、基础线层和拾取。只有二维投影与球面生成稳定后，才进入高级视觉效果。

## 16. 推荐的首个可交付版本

首个球面 MVP 不需要包含完整气候和精致 3D。当前范围包括：

1. Icosphere level 5 或 level 6；
2. 球面板块；
3. 大陆与岛屿；
4. 三维无缝高程；
5. 海洋与湖泊基础分类；
6. 球面 Voronoi 单元；
7. 离散高度图、海岸线和等高线；
8. 可旋转、缩放和拾取的固定半径 Globe。
9. 仅由地形和均匀径流驱动的球面河流。

这个版本已经能够验证最重要的架构假设：

- 世界生成是否真正与矩形边界无关；
- 左右接缝是否连续；
- 二维投影和三维位置是否引用同一 region；
- 当前基于邻接关系的生成算法是否能够平滑迁移。

在上述假设验证通过后，再继续迁移气候、编辑和高质量渲染，整体风险会明显低于一次性重写。

## 17. 最终建议

项目应将未来的全球模式定义为“球面地理模拟 + 多视图渲染”，而不是“二维地图增加一个球形展示效果”。

推荐优先级如下：

1. Icosphere、球面生成与球面 Voronoi 已经成为唯一世界数据源；
2. 当前 3D Globe 用于验证大陆、高程、海岸线、等高线和纯地形河流；
3. 下一步实现等距圆柱投影和 seam splitting；
4. 随后让二维高度图、海岸线和拾取消费投影后的同一批 region；
5. 最后扩展气候水文与二三维编辑同步。

墨卡托可以作为二维视图之一，但不应成为全球数据模型，也不应作为完整球面纹理的唯一输出格式。对于需要覆盖两极、供 3D 球体采样的纹理，等距圆柱投影应当优先实现。
