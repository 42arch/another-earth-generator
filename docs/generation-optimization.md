# 生成、渲染与水文优化实现记录

本文描述 2026-09-05 的实现；早期球面迁移与 3D Globe 方案保留为历史设计。算法入口仍是 `src/core/spherical/spherical-world-generator.ts`。

## 1. 后台生成与增量依赖

`generation-plan.ts` 明确列出每个参数最早影响的阶段，使用穷尽类型约束防止新增参数漏配。阶段按以下顺序级联：

```text
world → elevation → hydrology → rivers → human → transport
      → trade → cultures → polities → religions
```

UI 保留生成参数草稿，点击“应用全部更改”后按最早受影响阶段统一更新；显示模式、图层、线框、自转等外观设置直接更新渲染。Worker 内的 `GenerationRuntime` 再将请求与上次成功生成的参数比较，避免只依赖 UI 提示而漏算。

“图层与设置”面板将通用设置和图层参数放在同一入口。种子、精度、基础地形和行星尺度位于通用折叠区；选择主题、分析层或要素图层后显示关联参数。勾选框控制显隐，点击名称选择并开启图层，多要素图层可以同时显示。参数定义在 `src/ui/state/parameter-catalog.ts`，关联关系在 `src/ui/state/layer-settings.ts`；共享参数直接引用同一份世界草稿，切换或隐藏图层不会丢失修改。

`GenerationClient` 保留一个执行中请求和一个合并后的待执行请求。已经过时的结果不展示；这些结果实际修改过的阶段仍累积到最终结果，用于使渲染缓存失效。主动取消通过终止 Worker 实现，下一次请求创建新 Worker。计算失败会丢弃 Worker 内可能已部分修改的数据，重试从完整世界开始。UI 在失败、取消和正常完成后均清理加载状态，提供阶段提示与重试入口。

Worker 持有生成器和权威世界数据。主线程接收结构化克隆快照；拓扑版本不变时省略网格快照。快照显式包含 Voronoi 数组，主线程恢复索引，不重新计算 Voronoi。当前没有转移权威 TypedArray 的所有权，因此仍有数据复制成本，也会同时保留生成数据和渲染快照。后续若优化传输，应先测量复制耗时和内存，再考虑分阶段快照或双缓冲。

`WorldEngine.lastGenerationTimings` 暴露阶段累计耗时、生成 `total` 与主线程 `presentation` 耗时。Worker 排队和消息传输不包含在这些指标内；这些指标不等于用户端完整等待时间。

为保证增量计算可复现，高程重算从原始板块状态重新开始；海上接触与门户排序使用 `baseProsperity`，避免读取上一轮贸易已修改的繁荣度。

## 2. 图层缓存与按需绘制

二维和三维视图都按图层缓存几何与材质。关闭图层仅隐藏；首次开启或依赖数据失效后才构建。数据更新按 `layer-dependencies.ts` 选择失效图层，例如宗教修改不会重建河网和道路，水文修改会重建湖岸、等高线及下游图层。三维海岸接缝携带专题颜色，数据或显示模式变化时额外刷新。

显示模式主要更新表面颜色和相关专题层；贸易模式中已有道路和航线的透明度直接更新。二维视图未激活时推迟构建。拓扑、投影或渲染半径变化时清理对应缓存；单层替换和视图销毁时释放几何与材质。

动画回调继续驱动相机控制器，但相机和数据均未变化时跳过 GPU 绘制与标签布局；页面隐藏时跳过绘制。自转、相机阻尼、选择、窗口尺寸或参数变化会触发必要刷新。首次开启复杂图层的几何构建仍在主线程执行，尚未迁入 Worker。

## 3. 物理量和参数迁移

| 字段 | 当前语义 |
| --- | --- |
| `planetRadius` | 渲染尺寸，只影响视图 |
| `physicalRadiusMeters` | 物理半径，默认 6,371,000m；用于坡度距离和湖泊库容 |
| `physicalElevationMeters` | 地形物理高程，米 |
| `hydrologyElevationMeters` | 包含实际湖面的水文表面，米 |
| `baseElevation` / `elevation` | 非线性显示高程，不再输入湖盆、河流排水和地形雨计算 |
| `lakes.surfaceElevation` / `bottomElevation` | 湖面与湖底高程，米 |
| `lakes.area` | 单位球面面积，球面度；乘物理半径平方得到平方米 |
| `lakes.volume` | `Float64Array`，立方米 |
| `lakeMinDepthMeters` | 最小候选湖盆深度，默认 72m，替代 `lakeMinDepth` |

库容按 `Σ(max(0, 水面米高程 − 地形米高程) × regionArea × physicalRadiusMeters²)` 积分。Priority-Flood 的高程微扰使用 0.01m。已有河源高度控制 `riverMinSourceElevation` 保留原显示尺度，在河流入口转换为米。

手动保存的参数对象需要将旧 `lakeMinDepth` 改为 `lakeMinDepthMeters` 并重新选定米制阈值；不存在统一线性换算，因为旧值基于非线性显示高程。参数对象也应补齐新的物理半径和降水校准字段。改造后的同种子地图可能与旧版本不同；确定性保证针对同一实现和完整参数集。

河流流量、湖泊入流与蒸发仍是面积加权的模型归一化量，不能解释为 m³/s。米制库容目前没有参与具有真实时间步长的蓄水积分。

## 4. 气候与湖泊反馈

地形雨使用 `Δh米 / (球面角距离 × physicalRadiusMeters)` 的无量纲坡度。水汽在不等面积单元间输送时按源/目标面积比转换密度，以保持该输送项的面积积分。源、汇、截断和降水校准仍是经验模型，不能据此宣称整个气候系统严格守恒。

温度保留 12 个月采样，水汽和径流保留 4 个代表季节。新增 `precipitationCalibration ∈ [0,1]`：默认 1 保留 P50/P90/P98 分位锚定；0 使用固定的 `rate × 70000` 年降水换算，上限 4000mm；中间值线性混合。固定换算有助于观察蒸发源强变化，仍不是经过观测标定的物理降水求解器。

湖泊结冰使用湖盆内面积加权的完整月温度序列。最热月不高于 0℃ 时归为 `Subglacial`，否则最冷月不高于 0℃ 时归为季节冻湖，其余为不冻湖；开放水面比例取月均温大于 0℃ 的月份占比。这里的 `Subglacial` 是沿用的显示分类，不意味着模型已经求解冰盖厚度或地热融水。

先构建 L1 最大地形湖盆和初始气候、河网，再执行最多 4 轮 L2 水平衡—气候—径流反馈。每轮将实际湖泊映射回原始湖盆；已干涸湖盆使用原始排水盆地评估入流，允许重新恢复。相邻迭代的入流估计采用 0.5 阻尼，海洋与温度背景在本次求解中复用。

当湖泊单元掩码不再变化且最大相对入流变化不超过 2% 时停止，否则达到上限后返回最后一次完整结果。`hydrologyDiagnostics` 报告迭代次数、是否收敛、最大入流变化及变化单元数。达到上限不代表已经收敛；当前诊断也不是严格的水量收支误差。

## 5. 验证与边界

本次 `pnpm run test` 通过 8 个文件、48 项测试，包含原有测试及以下新增覆盖：

- 九类参数分别增量更新后，与相同参数完整生成逐字段比较。
- 网格快照恢复、图层懒构建和依赖失效。
- 连续请求合并、过期结果阶段累积、取消后旧 Worker 事件隔离、启动失败重试。
- UI 防抖、失败恢复、并发加载状态及取消清理。
- 湖泊温度周期分类、三个种子的米制库容和迭代上限、显示高程独立性、关闭分位校准后的蒸发响应。

本地开发页验证了默认细分等级生成以及二维 Equal Earth 投影切换，控制台未发现错误。浏览器内“演化”按钮及加载中取消按钮的端到端交互尚未完成验证；对应状态机已由测试覆盖。未运行生产构建或 lint，也尚未取得改造前后的同机性能基准。
